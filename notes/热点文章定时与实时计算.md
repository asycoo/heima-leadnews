# 热点文章：定时计算 + 实时计算

> 讲义：day10《热点文章-定时计算》、day11《新热文章-实时计算》  
> 代码：`heima-leadnews-article`（计算 / XXL-JOB / KafkaStream）、`heima-leadnews-behavior` / `comment`（发行为消息）

---

## 0. 先建立画面：首页为什么要「热点」？

APP 频道首页如果直接按发布时间查 MySQL：

- 流量大时库压力大  
- 新文章永远顶前面，**不一定是大家正在看的热文**

项目做法：按点赞 / 评论 / 阅读 / 收藏算出**分值**，把每个频道 Top30（外加推荐 `__all__`）塞进 Redis；首页优先读缓存。

两条线互补：

| | 定时计算（day10） | 实时计算（day11） |
| --- | --- | --- |
| 触发 | XXL-JOB 每天跑一次 | 用户点赞/阅读/评论/收藏立刻发 Kafka |
| 数据范围 | 近若干天文章全量算分 | 单篇增量行为 → 窗口聚合 → 改分 |
| 目的 | 先把 Redis 热点池铺好 | 当天热度变化马上反映到池子里 |
| 关键组件 | XXL-JOB + Feign 频道列表 | Kafka + Kafka Streams |

```text
Redis key：hot_article_first_page_{channelId}
         以及 hot_article_first_page___all__（推荐）
value：JSON 数组，最多 30 条 HotArticleVo（文章字段 + score）
```

名词小抄：

| 词 | 人话 |
| --- | --- |
| 分值 score | 阅读×1 + 点赞×3 + 评论×5 + 收藏×8 |
| XXL-JOB | 分布式定时调度：admin 触发，article 当执行器干活 |
| Kafka Streams | 嵌在 article 进程里的流处理库；按窗口聚合行为消息 |
| UpdateArticleMess | 行为侧发出的「某文章某类型 +1/-1」 |
| ArticleVisitStreamMess | Stream 聚合后的「某文章窗口内四类增量」 |

---

## 1. 分值公式（两条线共用）

```text
score = views
      + likes      * 3
      + comment    * 5
      + collection * 8
```

常量：`ArticleConstants.HOT_ARTICLE_LIKE_WEIGHT` 等。

实时更新进 Redis 时还会 **`score * 3`**，给「正在热」的文章加权，更容易挤进 Top30。

## 2. 定时计算（XXL-JOB）

### 2.1 流程

```text
XXL-JOB admin 到点触发
  → article 执行器 @XxlJob("computeHotArticleJob")
  → HotArticleService.computeHotArticle()
       ① 查近 N 天未删除/未下架文章（findArticleListByLast5days）
       ② 每篇算 score → HotArticleVo
       ③ Feign 拉全部频道
       ④ 每个频道取 Top30 写入 Redis
       ⑤ 全量再取 Top30 写入推荐 key（__all__）
```

核心骨架：

```java
public void computeHotArticle() {
    // 方法名 last5days；实战工程常改成 minusDays(200) 方便演示数据
    Date dateParam = DateTime.now().minusDays(5).toDate();
    List<ApArticle> list = apArticleMapper.findArticleListByLast5days(dateParam);
    List<HotArticleVo> scored = computeHotArticle(list); // 算分
    cacheTagToRedis(scored); // 按频道 + 推荐缓存
}
```

`sortAndCache`：按 score 倒序，超过 30 截断，`cacheService.set(key, JSON)`。

### 2.2 首页怎么用缓存

`ApArticleServiceImpl#load2`：`firstPage==true` 时先读

```text
hot_article_first_page_ + dto.getTag()
```

有数据直接返回；没有再走原来的 DB 列表。  
控制器 `/load` 首页传 `firstPage=true`。

### 2.3 XXL-JOB 配置（调度中心 + 执行器）

#### （1）调度中心 admin：Docker 部署

admin 只负责页面管理 + 到点触发，**不跑热点业务**；用 Docker 起即可，不必源码启动。

**步骤 A：先初始化调度库 SQL**

脚本位置（资料）：`xxl-job/doc/db/tables_xxl_job.sql`  
作用：建库 `xxl_job`，再建调度中心用的表（容器连不上空库会起不来）。

脚本开头大致是：

```sql
CREATE database if NOT EXISTS `xxl_job` ...;
use `xxl_job`;
-- 随后 CREATE TABLE ...
```

表各自干什么（人话）：

| 表 | 干什么 |
| --- | --- |
| `xxl_job_info` | 任务配置：Cron、JobHandler、路由策略、超时重试等（页面「任务管理」落库） |
| `xxl_job_group` | 执行器分组：AppName、机器地址列表（「执行器管理」） |
| `xxl_job_registry` | 在线注册：执行器心跳上报的地址，admin 靠它知道谁活着 |
| `xxl_job_log` | 每次调度/执行日志：成功失败、触发时间、执行器地址 |
| `xxl_job_log_report` | 按天汇总的运行报表（成功/失败/运行中数量） |
| `xxl_job_logglue` | GLUE 模式源码版本历史（本项目用 BEAN 模式，平时不怎么碰） |
| `xxl_job_lock` | 调度锁，集群下保证同一时刻调度不乱抢 |
| `xxl_job_user` | 登录账号（默认 `admin/123456`） |

在已有 MySQL 执行该 SQL 即可（课程机常用 `192.168.200.130:3306`）。

**步骤 B：拉镜像并起容器**

```shell

--spring.datasource.username=root \
```

| 点 | 说明 |
| --- | --- |

| `-p 8888:8080` | 宿主机 8888 → 容器内 admin 8080 |
| `-v /tmp:/data/applogs` | 调度日志挂到宿主机 |

访问：`http://192.168.200.130:8888/xxl-job-admin`（默认 `admin/123456`）。

记住：Docker 只部署 **admin**；真正算热点仍是 `leadnews-article` 当执行器注册上来。

## 3. 实时计算（Kafka + Kafka Streams）

### 3.1 为什么还要实时？

定时一天一次，白天爆火的文章要等夜里才进池。  
行为一发生就发消息，Stream 聚合同一文章短窗口内的增量，再改库、改 Redis。

```text
behavior / comment
  --发--> hot.article.score.topic
              │
              ▼
     article 内 Kafka Streams（约 10s 窗口按 articleId 聚合）
              │
              ▼
     hot.article.incr.handle.topic
              │
              ▼
     ArticleIncrHandleListener
              → updateScore：改 DB 行为数 + 算分*3 + 替换 Redis Top30
```

### 3.2 Topic 与消息体

常量 `HotArticleConstants`：

| 常量 | Topic | 谁写 / 谁读 |
| --- | --- | --- |
| `HOT_ARTICLE_SCORE_TOPIC` | `hot.article.score.topic` | behavior/comment 生产；Streams 消费 |
| `HOT_ARTICLE_INCR_HANDLE_TOPIC` | `hot.article.incr.handle.topic` | Streams 生产；article `@KafkaListener` 消费 |

行为消息 `UpdateArticleMess`：

```text
articleId + type(COLLECTION|COMMENT|LIKES|VIEWS) + add(+1/-1)
```

聚合结果 `ArticleVisitStreamMess`：

```text
articleId + view/collect/comment/like（窗口内累加增量）
```

### 3.3 行为侧发 Kafka（配置）

behavior（点赞、阅读等）需要生产者配置，Nacos / yml 示例：

```yaml
spring:
  application:
    name: leadnews-behavior
  kafka:
    bootstrap-servers: 192.168.200.130:9092
    producer:
      retries: 10
      key-serializer: org.apache.kafka.common.serialization.StringSerializer
      value-serializer: org.apache.kafka.common.serialization.StringSerializer
```

| 配置 | 干什么 |
| --- | --- |
| `bootstrap-servers` | 发消息到哪台 Kafka |
| `producer.retries` | 发送失败重试次数 |
| `key-serializer` / `value-serializer` | key/value 按 String 发出（内容是 JSON） |

发送示例（点赞）：

```java
UpdateArticleMess mess = new UpdateArticleMess();
mess.setArticleId(dto.getArticleId());
mess.setType(UpdateArticleMess.UpdateArticleType.LIKES);
mess.setAdd(dto.getOperation() == 0 ? 1 : -1); // 点赞 / 取消
kafkaTemplate.send(HotArticleConstants.HOT_ARTICLE_SCORE_TOPIC, JSON.toJSONString(mess));
```

阅读同理，`type=VIEWS`，`add=1`。评论服务也会往同一 Topic 发 `COMMENT`。

### 3.4 article 侧两套 Kafka 配置（别混）

article 里同时有：

1. **普通 Spring Kafka**：给 `ArticleIncrHandleListener`（`@KafkaListener`）用  
2. **Kafka Streams**：给 `HotArticleStreamHandler` 聚合用  

`bootstrap.yml`：

```yaml
spring:
  application:
    name: leadnews-article
  kafka:
    bootstrap-servers: 192.168.200.130:9092
    consumer:
      group-id: ${spring.application.name}
      key-deserializer: org.apache.kafka.common.serialization.StringDeserializer
      value-deserializer: org.apache.kafka.common.serialization.StringDeserializer

# 下面这块只给 Streams（KafkaStreamConfig 读取）
kafka:
  hosts: 192.168.200.130:9092
  group: ${spring.application.name}
```

`spring.kafka` 每一项：

| 配置 | 干什么 |
| --- | --- |
| `spring.kafka.bootstrap-servers` | Listener 连的 Kafka 地址 |
| `spring.kafka.consumer.group-id` | 消费组，一般等于服务名 `leadnews-article` |
| `key-deserializer` / `value-deserializer` | 消息按 String 反序列化（内容是 JSON 文本） |

`kafka.*`（Streams 自定义前缀）每一项：

| 配置 | 干什么 |
| --- | --- |
| `kafka.hosts` | Streams 连的 broker（和上面 bootstrap 通常同一个 IP） |
| `kafka.group` | 用来拼 Streams 的 `application.id` / `client.id` |

### 3.5 KafkaStreamConfig：每个注解 / 每个 props 干什么

```java
@Setter @Getter
@Configuration
@EnableKafkaStreams
@ConfigurationProperties(prefix = "kafka")
public class KafkaStreamConfig {
    private String hosts;   // ← kafka.hosts
    private String group;   // ← kafka.group

    @Bean(name = KafkaStreamsDefaultConfiguration.DEFAULT_STREAMS_CONFIG_BEAN_NAME)
    public KafkaStreamsConfiguration defaultKafkaStreamsConfig() { ... }
}
```

类上注解：

| 注解 / 成员 | 干什么 |
| --- | --- |
| `@Configuration` | 这是配置类，Spring 会扫描 |
| `@EnableKafkaStreams` | **打开** Kafka Streams；没有它，后面的 `KStream` Bean 不会跑起来 |
| `@ConfigurationProperties(prefix="kafka")` | 把 yml 里 `kafka.hosts` / `kafka.group` 绑到字段 |
| `hosts` / `group` 字段 | 供下面 props 使用 |
| `@Bean(...DEFAULT_STREAMS_CONFIG...)` | 向 Spring 注册「Streams 默认配置」；名字必须用这个常量，框架才认 |

`defaultKafkaStreamsConfig()` 里每一项 props：

| props | 取值示例 | 干什么 |
| --- | --- | --- |
| `BOOTSTRAP_SERVERS_CONFIG` | `kafka.hosts` → `192.168.200.130:9092` | Streams 连哪台 Kafka |
| `APPLICATION_ID_CONFIG` | `group + "_stream_aid"` → `leadnews-article_stream_aid` | Streams 应用身份；消费位点、状态存储都挂在它上面，**换了等于新应用重来** |
| `CLIENT_ID_CONFIG` | `group + "_stream_cid"` → `leadnews-article_stream_cid` | 客户端名字，方便在 Kafka/监控里区分 |
| `RETRIES_CONFIG` | `10` | 内部请求失败重试次数 |
| `DEFAULT_KEY_SERDE_CLASS_CONFIG` | `Serdes.String()` | key 按字符串序列化 |
| `DEFAULT_VALUE_SERDE_CLASS_CONFIG` | `Serdes.String()` | value 按字符串序列化（本项目消息都是 JSON 字符串） |

说明：类里还有个没用上的 `MAX_MESSAGE_SIZE` 常量，可忽略。

依赖：`spring-kafka` + `kafka-streams`。

### 3.6 HotArticleStreamHandler 和 Listener 怎么衔接（重要）

两层分工：

```text
启动时（只执行一次）：
  Spring 发现 @EnableKafkaStreams
    → 创建 StreamsBuilder
    → 调用 HotArticleStreamHandler#kStream(@Bean)  ← 业务代码不会手动调
    → 把「读谁、怎么聚合、写谁」装进拓扑
    → Streams 进程开始监听

运行时（每来消息就自动跑拓扑）：
  score.topic 原始行为
    → Streams 按图纸聚合
    → 写出 incr.handle.topic

运行时（另一条线）：
  ArticleIncrHandleListener#onMessage
    ← 消费的就是 Streams 处理好的聚合结果
    → updateScore
```

记住：

- `kStream()`：**启动时装流水线**，不是每条消息调一次  
- `onMessage()`：**每条聚合结果调一次**，收的是 Handler 写到 `incr.handle.topic` 的数据，不是行为侧原始消息  

`HotArticleStreamHandler` 拓扑在干什么：

```text
读 hot.article.score.topic
  → map：key=articleId，value="LIKES:1"
  → groupBy 文章 id
  → 10 秒时间窗口
  → aggregate：累加成 "COLLECTION:x,COMMENT:y,LIKES:z,VIEWS:w"
  → 转成 ArticleVisitStreamMess JSON
  → 写出 hot.article.incr.handle.topic
```

窗口作用：短时间内同一文章多次点赞/阅读**合并成一条**，减轻后面改库改缓存次数。

### 3.7 Listener 更新库 + Redis

```java
@KafkaListener(topics = HotArticleConstants.HOT_ARTICLE_INCR_HANDLE_TOPIC)
public void onMessage(String mess) {
    // mess = Streams 聚合后的 ArticleVisitStreamMess JSON
    apArticleService.updateScore(JSON.parseObject(mess, ArticleVisitStreamMess.class));
}
```

`updateScore`：

```text
1. updateArticle：views/likes/comment/collection += 窗口增量，写 MySQL
2. computeScore → 再 * 3
3. replaceDataToRedis(频道 key)
4. replaceDataToRedis(推荐 __all__ key)
```

`replaceDataToRedis` 规则：

- 池子里已有该文 → 只改 score  
- 没有且未满 30 → 直接加入  
- 已满 30 → 和最低分比较，更大则换掉  
- 最后再按 score 倒序写回 Redis

## 5. 和别的组件别混

| 组件 | 在本需求里干什么 |
| --- | --- |
| MySQL `ap_article` | 行为计数真相；定时全量算分的数据源 |

| XXL-JOB | 定时触发全量算分 |
| Feign → wemedia | 定时任务拉频道列表，按频道切缓存 |

| Kafka Streams | 同文章短窗口聚合，削峰 |
| behavior / comment | 只负责记行为并往 score.topic 丢消息，不算热点 |

## 6. 快速自问

1. 定时和实时最终都写哪里？→ 同一套 Redis 热点 key。  
2. XXL-JOB 为什么不用 `@Scheduled`？→ 集群重复执行、改 Cron 要改代码、缺失败重试与统一管理。  
3. JobHandler 对不上会怎样？→ admin 触发了，执行器找不到 Bean 方法。  
4. 为什么要两个 Topic？→ 行为原始事件与聚合结果解耦；Streams 中间算，Listener 专心改库改缓存。  
5. `kStream` 谁调用？→ 启动时 Spring 调一次装拓扑；`onMessage` 才是每条聚合结果调一次。  
6. Listener 收的是原始点赞吗？→ 不是，收的是 Streams 写到 `incr.handle.topic` 的聚合结果。  
7. 实时为何 `score * 3`？→ 抬高新热，更容易挤进已有 Top30。  
8. `kafka.hosts` 和 `spring.kafka.bootstrap-servers` 为何都配？→ 前者给 Streams，后者给 `@KafkaListener`。

---

## 一句话

**定时：XXL-JOB 每天拉文章算分，按频道灌 Redis Top30；实时：行为发 `hot.article.score.topic`，Kafka Streams 10 秒聚合后进 `hot.article.incr.handle.topic`，article 改库并按「已有则更新 / 更高则替换」维护同一套热点缓存。**
