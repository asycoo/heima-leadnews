# 文章审核流程实现

> 对应课程：day04 自动审核 → day05 定时发布 → day06 上下架  
> 主要代码：`WmNewsAutoScanServiceImpl`、`WmNewsTaskServiceImpl`、`TaskServiceImpl`（schedule/Redis）、`ApArticleServiceImpl#saveArticle`

---

## 0. 先建立画面（最重要）

### 业务在干什么？

自媒体作者在 **wemedia 后台** 写好一篇稿，点「发布」。  
系统不能直接给 APP 用户看，要先过安检（有没有违禁词、违禁图）。  
安检通过后，再在 **article 服务** 里生成 APP 端真正展示的那篇文章。

可以记成两套库、两个角色：


|     | 自媒体侧               | APP 侧                  |
| --- | ------------------ | ---------------------- |
| 服务  | `leadnews-wemedia` | `leadnews-article`     |
| 表   | `wm_news`（作者的稿）    | `ap_article` 等（读者看到的稿） |
| 谁先有 | 作者一点发布就有           | **只有审核通过才创建**          |


所以审核服务跑在 **wemedia** 里；通过后要「打电话」给 article 去建稿——这个电话就是 **Feign**。

### 一篇稿的人生（按时间顺序）

```text
作者点发布
   ↓
稿子存进 wm_news，状态=「待审核」
   ↓
等到设定的发布时间（可立刻，也可明天）
   ↓
开始安检：文本 → 敏感词 → 图片
   ↓ 通过
打电话给 article：帮我建一篇 APP 文章（生成一个全局唯一 ID）
   ↓
把这个 ID 记回 wm_news，状态改成「已发布」
   ↓
顺带生成静态详情页、同步搜索……
   ↓
以后运营点上下架：再发条消息通知 article 改展示开关
```



### 名词小抄（懵的时候回来看）


| 词                     | 人话                      |
| --------------------- | ----------------------- |
| 待审核 status=1          | 已提交，等安检                 |
| 审核失败=2 / 人工=3 / 已发布=9 | 安检结果；9 表示 APP 侧已有稿      |
| `@Async`              | 换个线程慢慢干，发布接口先返回成功       |
| 延迟队列 / schedule       | 闹钟：到 `publishTime` 再开始审 |
| Feign                 | 微服务之间像调本地方法一样发 HTTP     |
| 雪花 ID                 | 分布式下生成不重复的 Long 主键      |
| MinIO                 | 图片/静态页存的地方              |
| Kafka                 | 发消息解耦：这边改完，那边自己改        |


`wm_news.status` 完整表：


| 值   | 含义             |
| --- | -------------- |
| 0   | 草稿             |
| 1   | 待审核            |
| 2   | 审核失败           |
| 3   | 转人工            |
| 4   | 人工审核通过         |
| 8   | 审核通过（待发布）      |
| 9   | 已发布（APP 文章已生成） |

## 1. 第一步：作者点发布会发生什么？

入口：`WmNewsServiceImpl#submitNews`

用人话走一遍：

1. 把标题、内容、封面等存进 `wm_news`
2. 如果是**草稿** → 到此结束，不审
3. 如果是**提交发布** → 记素材关系，然后**安排审核**（不是同步卡在这里审完）

day13 实际代码安排审核的方式：

```java
// 把「到 publishTime 再审这篇稿」交给延迟任务服务
wmNewsTaskService.addNewsToTask(wmNews.getId(), wmNews.getPublishTime());
```

发布接口很快返回成功；真正安检在后台做。

## 2. 为什么不是「发布后立刻审」？——延迟队列



### day04 曾经怎么做

```java
wmNewsAutoScanService.autoScanWmNews(wmNews.getId()); // 方法上有 @Async
```

含义：另起线程马上安检。  
解决的问题：安检很慢（调阿里云、下图片），不能堵死发布接口。

### 为什么 day05 又改成进延迟队列？

因为产品要 **定时发布**：作者可以选「明天早上 8 点」才见报。

- 立刻异步审：现在就审完、现在就建 APP 文章 → 读者可能提前看到 → **不符合定时发**  
- 延迟队列：闹钟设在 `publishTime`，到点才 `autoScanWmNews` → 到点才上 APP

```text
publishTime = 现在     → 很快被拉去审（效果≈立刻审）
publishTime = 明天 8 点 → 一直等到明天 8 点再审
```

实现轮廓：

```text
wemedia addNewsToTask
  → Feign → schedule.addTask（执行时间=publishTime，参数里带文章 id）
schedule：MySQL 落库 + Redis（list / zset）管理到期
wemedia 定时 poll
  → Feign → schedule.poll → 拿到到期任务 → autoScanWmNews(id)
```

**记住**：`@Async` 解决「别卡住我」；延迟队列解决「等到点再干」。两个不是一回事。

## 2.1 schedule 怎么用 Redis 做延迟队列？（day05 核心）

服务：`leadnews-schedule`，类：`TaskServiceImpl`。  
思路：**MySQL 保底持久化 + Redis 加速调度**；Redis 里用 **list（可立刻执行）+ zset（即将到期）** 两种结构。

### 为什么要 DB + Redis 两套？

| 存哪 | 干什么 |
| --- | --- |
| MySQL `taskinfo` / `taskinfo_logs` | 任务不丢（进程挂了还能恢复）；通用延迟服务的数据安全 |
| Redis | 高频 add / poll / 按时间取，比每次扫库快 |

讲义三个为什么：

1. **为什么落库？** 通用延迟服务，要持久化，防丢任务。  
2. **为什么 list + zset 两种？** 结构不同、复杂度不同：list 适合「立刻可消费」队列；zset 按 score（执行时间戳）排序，适合「还没到点、但快到了」的候场。  
3. **为什么 zset 不把所有未来任务都塞进去？** 任务可能非常多，只缓存 **未来约 5 分钟内** 要执行的，避免 Redis 爆、也避免大 key 拖慢；更远的只在 DB，靠定时同步刷进来。

### Redis Key 设计

```text
key 后缀 = taskType + "_" + priority   （文章审核例如 NEWS_SCAN_TIME 的类型和优先级）

topic_{type}_{priority}   → Redis List   已经到点、可被 poll 的任务
future_{type}_{priority}  → Redis ZSet   未来 5 分钟内到期的任务（score = executeTime 毫秒）
```

常量：`ScheduleConstants.TOPIC = "topic_"`，`FUTURE = "future_"`。

### 添加任务 `addTask`

```text
① addTaskToDb
     写 taskinfo，写 taskinfo_logs（status=初始化）
     回填 taskId
② addTaskToCache（仅 DB 成功后）
     executeTime <= 现在          → lLeftPush 进 topic_xxx（list）
     现在 < executeTime <= 现在+5分钟 → zAdd 进 future_xxx（zset，score=执行时间）
     executeTime > 现在+5分钟      → 只在 DB，暂不进 Redis
```

对应代码逻辑：

```java
String key = taskType + "_" + priority;
if (executeTime <= now) {
    cacheService.lLeftPush("topic_" + key, json);
} else if (executeTime <= now + 5分钟) {
    cacheService.zAdd("future_" + key, json, executeTime);
}
// 更远的：不写 Redis，等 reloadData / 时间靠近后再进
```

### 消费任务 `poll`（wemedia 来拉）

```text
只从 list 取：lRightPop("topic_" + type + "_" + priority)
取到 → 解析 Task → updateDb 标记已执行（删 taskinfo、改日志）
取不到 → 返回空（还没到期，或未来任务还在 zset 里没刷过来）
```

所以：**poll 从不直接扫 zset**；到期任务必须先被刷进 list。

### 未来数据定时刷新 `refresh`（每分钟）

把「已经到点」的 zset 成员挪到 list：

```text
@Scheduled(cron = "0 */1 * * * ?")
加分布式锁 FUTURE_TASK_SYNC（多实例只跑一份）
scan("future_*")
对每个 futureKey：
  zRangeByScore(futureKey, 0, 当前时间)  // score≤现在 = 到期了
  pipeline：从 zset 删掉这些，推进对应的 topic_ list
```

### 数据库同步到 Redis `reloadData`

```text
@PostConstruct + @Scheduled(每 5 分钟)
先 clearCache（清掉 topic_* / future_*）
再查 DB：executeTime < 现在+5分钟 的任务
逐条 addTaskToCache（该进 list 进 list，该进 zset 进 zset）
```

「现在+5分钟」代码就是：

```java
Calendar calendar = Calendar.getInstance(); // 当前时间
calendar.add(Calendar.MINUTE, 5);          // 往后推 5 分钟
// 查库：executeTime < calendar.getTime()
```

作用：重启、Redis 丢数据、或「更远任务进入 5 分钟窗口」后，把 DB 里该上场的任务补回缓存。

### 和文章审核怎么接上

```text
发布：wemedia → Feign addTask（DB+可能进 Redis）
调度：schedule 每分钟 refresh（zset→list）；每 5 分钟/启动 reloadData（DB→Redis）
消费：wemedia @Scheduled 每秒 scanNewsByTask
        → Feign poll（只 pop list）
        → 有任务则 autoScanWmNews
```

人话版时间线举例：

```text
现在 10:00，publishTime=10:20
  → 只写 DB（20 分钟后，超过 5 分钟窗口）

约 10:15 reloadData
  → 任务进入 future_ zset（score=10:20）

10:20 之后某次 refresh
  → 从 zset 搬到 topic_ list

wemedia poll
  → pop 到任务 → 开始审核
```


若 `publishTime` 就是现在：`addTask` 直接进 list，下一秒 poll 就能审。

### 容易懵的点（FAQ）

#### 1. `scan("future_*")` 干什么？

`refresh` 不知道会有多少种 `taskType_priority`，不能写死 key。  
`scan` 按模式把 Redis 里所有 `future_` 开头的 zset key 找出来（如 `future_100_50`），再逐个把到期任务刷进对应 `topic_`。

封装在 `CacheService.scan`；底层是 Redis **`SCAN`**（游标迭代），不是一次扫完的 **`KEYS`**。

#### 2. 为什么说 `KEYS` 在 key 多时会堵死 Redis？

Redis 执行命令基本是**单线程串行**：同一时刻主要只跑一条命令。

`KEYS future_*` 要遍历大量 key 并匹配，**整次结束才返回**。这段时间别的 `GET`/`LPOP`/`ZADD` 都得排队等，看起来就像 Redis 卡住。

`SCAN` 分多轮、每轮干一点就返回，轮与轮之间可以插着处理别的客户端命令，所以更适合生产（很多环境直接禁用 `KEYS`）。

#### 3. 代码里 `scan` 怎么没写每次扫多少？

业务侧只写了模式：

```java
cacheService.scan(ScheduleConstants.FUTURE + "*");
```

**每批提示数量**写在 `CacheService` 里：

```java
connection.scan(new ScanOptions.ScanOptionsBuilder()
    .match(patten).count(10000).build())
```

这里的 **`COUNT 10000` 是 hint（建议）**，不是「每次一定返回 10000 个 key」。  
Redis 每轮大约检查这么多槽位；实际返回可多可少。  
另外：这个封装会把游标 next 完，在 Java 里攒成整个 `Set` 再返回——业务像「一次拿全」，Redis 底下仍是多轮 `SCAN`。

#### 4. `refreshWithPipeline` 里 `zRem` 的 `z` 是什么？

`z` = Redis **有序集合（sorted set / zset）** 相关命令。

```java
rPush(topic_key, tasks);  // 推进 list，供 poll 消费
zRem(future_key, tasks);  // ZREM：从 zset 删掉，避免重复刷新
```

`pipeline`：把这两步打包一次发给 Redis，少一次网络往返。

常见带 `z` 的命令：`ZADD` 加入（带 score）、`ZREM` 删除、`ZRANGEBYSCORE` 按分数取。

#### 5. list / zset / DB 再对照一眼

| 结构 | 角色 |
| --- | --- |
| MySQL | 所有任务的底账，防丢 |
| `future_` zset | 近 5 分钟内「还没到点」的候场（score=执行时间） |
| `topic_` list | 「已到点」可被 `poll` 拉走的队列 |

## 3. 第二步：安检到底查什么？`autoScanWmNews`

类：`WmNewsAutoScanServiceImpl`  
只有 `status == 1`（待审核）才往下走。

### 3.1 先把内容拆开

稿件正文是 JSON 块列表，例如文字块、图片块。代码会：

- 所有文字拼成一大段纯文本  
- 所有图片 URL（含封面）收进列表（图在 MinIO 上）



### 3.2 按顺序过安检（一步不过就停）

```text
① 阿里云审文本（标题+正文）
     明确违规 → status=2 失败
     拿不准   → status=3 转人工

② 自己库里的敏感词表（wm_sensitive）再扫一遍
     命中 → status=2

③ 审图：
     从 MinIO 把图下载下来
     Tess4j 识别图上的字 → 再过敏感词（防止「文字写成图」绕过）
     阿里云审图片本身 → 同样 block=2 / review=3

④ 全部过关 → 去 APP 侧建文章（下一节 Feign）
```

配置在 wemedia 的 yml 里，例如：

```yaml
aliyun:
  accessKeyId: xxx
  secret: xxx
  scenes: terrorism
tess4j:
  data-path: D:\workspace\tessdata
  language: chi_sim
```

## 4. 第三步：过关后如何生成 APP 文章？——Feign + 雪花



### 4.1 为什么要 Feign？

审核逻辑在 **wemedia**，APP 文章表在 **article**。  
不能直接 `new` 对方的 Service，所以：

```text
wemedia 里注入 IArticleClient
  → 像调本地方法：articleClient.saveArticle(dto)
  → 实际是 HTTP 打到 article 服务的 /api/v1/article/save
```

接口定义在公共模块 `heima-leadnews-feign-api`；  
article 里有个 `ArticleClient` Controller 真正执行保存。

调用方要记得开：

```java
@EnableFeignClients(basePackages = "com.heima.apis")
```

以及超时/降级（article 挂了别把审核线程拖死）：

```yaml
feign:
  hystrix:
    enabled: true
  client:
    config:
      default:
        connectTimeout: 2000
        readTimeout: 2000
```

更细的 Feign 说明见：`Feign远程调用工程实现.md`。

### 4.2 保存时 ID 为什么用雪花？

APP 文章表将来可能分库分表。如果每台库都 `id` 自增，合并后会撞号。  
所以 `ap_article`、`ap_article_config`、`ap_article_content` 用 **雪花算法** 生成 Long 型 ID：

```java
@TableId(value = "id", type = IdType.ID_WORKER)
private Long id;
```

```yaml
mybatis-plus:
  global-config:
    datacenter-id: 1
    workerId: 1
```

`saveArticle` 大致做：

```text
没有 id → 新建：文章 + 配置 + 内容（三张表，同一个雪花文章 id）
已有 id → 修改文章和内容
然后异步生成静态 HTML 上传 MinIO
把文章 id 返回给 wemedia
```

wemedia 拿到 id 后：

```text
wm_news.article_id = 这个雪花 id
wm_news.status = 9
reason = 审核成功
```

之后上下架、静态页、搜索都靠这个 `article_id` 把两边对上。

## 5. 同步 / 异步分别用在哪？（对照表）


| 你看到的代码                       | 同步还是异步  | 为什么                   |
| ---------------------------- | ------- | --------------------- |
| `submitNews` 返回给前端           | 同步      | 作者立刻知道「提交成功」          |
| `autoScanWmNews` 上的 `@Async` | 异步      | 安检慢，不占着发布/消费线程死等      |
| `addNewsToTask`              | 异步 + 延迟 | 先登记闹钟；到点再审            |
| Feign `saveArticle`          | **同步**  | 必须当场拿到 articleId 才能回填 |
| Freemarker 上传 MinIO          | 异步      | 静态化可以稍后再做             |
| 上下架发 Kafka                   | 异步消息    | wemedia 和 article 解耦  |


开启方式：启动类 `@EnableAsync`，方法 `@Async`。  
注意：同一个类里自己调自己，`@Async` 往往不生效，所以发布类调的是另一个 Service Bean。

## 6. Kafka 在这条链路里干什么？（不是审核本身）

**审稿过程不靠 Kafka。**  
Kafka 用在「审过 / 发布之后」两边服务要通气的时候。

### 最贴审核业务的：上下架（day06）

作者/运营在自媒体后台把已发布稿「下架」：

```text
wemedia：改自己的 wm_news.enable
       再发一条 Kafka：{ articleId, enable }
article：监听同一 Topic，改 ap_article_config（APP 是否展示）
```

为什么不用 Feign？上下架是通知型、可稍后一致，用消息更松耦合；审核建稿必须立刻拿 id，所以用 Feign。

配置长这样（示意）：

```yaml
# 生产者 wemedia
spring.kafka.bootstrap-servers: 192.168.200.130:9092
spring.kafka.producer.key-serializer: ...StringSerializer
spring.kafka.producer.value-serializer: ...StringSerializer

# 消费者 article
spring.kafka.consumer.group-id: ${spring.application.name}
spring.kafka.consumer.key-deserializer: ...StringDeserializer
spring.kafka.consumer.value-deserializer: ...StringDeserializer
```

代码形态：

```java
// 发
kafkaTemplate.send("wm.news.up.or.down.topic", json);

// 收
@KafkaListener(topics = "wm.news.up.or.down.topic")
public void onMessage(String message) { ... }
```

另外：静态页生成后还会 Kafka 通知搜索服务建 ES 索引（`article.es.sync.topic`），属于审核成功后的延伸，不是安检步骤。

## 7. 整条链路再走一遍（建议对着这个回忆）

```text
① 作者发布
     submitNews → 存 wm_news(status=1) → Feign addTask
     schedule：写 MySQL；近 5 分钟进 Redis zset/list

② 到点
     schedule.refresh 把到期任务从 zset 刷进 list
     wemedia 定时 poll（只 pop list）→ autoScanWmNews

③ 安检
     云审文本 → 敏感词 → 下图+OCR+云审图
     失败：改 status=2 或 3，结束
     成功：继续

④ 建 APP 稿
     Feign saveArticle → 雪花 ID 写三张表 → 异步静态化
     回填 article_id，status=9

⑤ 之后
     上下架 → Kafka → article 改配置
```

读代码时按这个顺序找：

1. `WmNewsServiceImpl#submitNews`
2. `WmNewsTaskServiceImpl#addNewsToTask` / `scanNewsByTask`
3. `TaskServiceImpl#addTask` / `poll` / `refresh` / `reloadData`（schedule + Redis）
4. `WmNewsAutoScanServiceImpl#autoScanWmNews`
5. `IArticleClient` → `ApArticleServiceImpl#saveArticle`
6. （可选）`WmNewsServiceImpl#downOrUp` + `ArtilceIsDownListener`

## 8. 快速自问（检验自己是否还记得）

1. 为什么有 `wm_news` 还有 `ap_article`？→ 作者稿 vs 读者稿，审过才同步。  
2. 为什么从立刻 `@Async` 改成延迟队列？→ 要支持定时发布。  
3. schedule 为什么 DB+Redis，Redis 为什么 list+zset？→ 持久化防丢；list 可消费，zset 按时间候场，且只缓存近 5 分钟。  
4. poll 为什么只 pop list？→ 到期任务由 refresh 从 zset 刷进 list 后再消费。  
5. 安检三板斧是什么？→ 云审文本、自管敏感词、下图 OCR+云审图。  
6. 过关为什么用 Feign 不用 Kafka？→ 要同步拿到雪花 articleId。  
7. Kafka 用在哪？→ 上下架（以及后来的 ES），不是安检主流程。

## 一句话版

**发布把「到点再审」交给 schedule（MySQL 持久化 + Redis list/zset 调度）；到点 wemedia poll 后做文本/敏感词/图片安检；通过则 Feign 在 article 用雪花 ID 生成 APP 文章；上下架再用 Kafka 通知 APP 侧。**
