## 0. 先搞清楚：这节课为什么突然讲 Kafka？

黑马头条里，自媒体把文章**上下架**时：

- **wemedia** 改自己的 `wm_news.enable`
- **article** 还要改 APP 侧配置（读者能不能看到）

两边是两个微服务。若用 Feign 强耦合调用，article 一时挂了，上下架就尴尬；而且以后还可能有搜索、缓存也要跟着变。

更合适的做法是：**改完自己的库，往消息中间件丢一条通知**；关心这件事的服务自己订阅、自己改。  
day06 选的中间件就是 **Kafka**。

所以后面 §3～§7 不是空讲组件，而是在铺：

```text
怎么装 → 怎么收发 → 怎么做到不太容易挂 → 生产者怎么发才稳 → 消费者怎么读才对
```

先把名词当「快递系统」记：

| Kafka 词 | 人话 |
| --- | --- |
| Topic | 快递分类 / 频道名（如上下架 topic） |
| Producer | 寄件人（wemedia 发消息） |
| Consumer | 收件人（article 收消息） |
| Broker | 快递站点（Kafka 服务器进程） |
| 集群 | 多个站点一起干，一个挂了别的还能转 |

## 3）安装配置：先有「场地」

老版本 Kafka **强依赖 ZooKeeper**（存集群元数据、节点信息），所以顺序是：

```text
先起 ZooKeeper → 再起 Kafka
```

课里用 Docker 举例：

- ZK：端口 `2181`
- Kafka：连 ZK，对外 `9092`

注意环境变量里的广告地址（如 `KAFKA_ADVERTISED_HOST_NAME`）要写成**客户端真实能访问的 IP**。  
写 `localhost` 在本机玩可能没事，别的机器连上后拿到错误地址，发送/消费会怪怪的。

装好以后，业务里通常配置：

```yaml
spring.kafka.bootstrap-servers: 192.168.200.130:9092
```

## 4）入门：怎么发、怎么收

### 最小心智模型

```text
生产者  --发到-->  Topic  --被-->  消费者拉取处理
```

原生客户端（课里 demo）大致是：

1. 配 `bootstrap.servers`（Kafka 地址）  
2. 配 key/value 的序列化（发）或反序列化（收）  
3. 生产者：`send(new ProducerRecord(topic, key, value))`，最后记得 `close`  
4. 消费者：设 `group.id` → `subscribe(topic)` → 循环 `poll` 取消息  

Spring 里更常见：`KafkaTemplate.send(...)` 发，`@KafkaListener` 收（项目上下架就是这样）。

### 一对一还是一对多？看消费者组

同一条消息、多个消费者时：

| 情况 | 效果 | 像什么 |
| --- | --- | --- |
| 多个消费者 **同一个** `group.id` | 组内只有一个人拿到这条 | 队列，分摊活 |
| 多个消费者 **不同** `group.id` | 每个组都能收到 | 广播 / 发布订阅 |

讲义总结：

- 同组多消费者 → 一对一（组内争抢）  
- 不同组 → 一对多（各组独立消费）

上下架场景：article 单独一个消费组订阅上下架 topic，收到就改配置即可。

## 5）高可用：别一台挂了全停

### 集群

Kafka 集群 = 多台 **Broker**。  
一台宕机，其他 Broker 还能对外服务——这是高可用的第一层。

### 副本（Replication）

重要数据会有多份拷贝：

- **Leader 副本**：负责该分区的读写  
- **Follower 副本**：向 Leader 同步  
- **ISR**：跟 Leader 同步得比较齐的 Follower 名单（in-sync replicas）

Leader 挂了怎么选新的：

1. **优先从 ISR 里选**（数据更齐，更可靠）  
2. ISR 都不行，才可能从其他 Follower 里选  

极端：副本全挂时，要么等 ISR 里有人活过来（可靠但慢），要么谁先活谁当 Leader（恢复快但可能丢数据）。  
课设了解即可；生产会结合副本数、`acks` 等一起设计。

## 6）生产者详解：发出去算不算成功？

### 同步发 vs 异步发

| 方式 | 写法直觉 | 特点 |
| --- | --- | --- |
| 同步 | `send(...).get()` | 堵住等结果，能立刻知道成败 |
| 异步 | `send(..., callback)` | 不堵当前线程，在回调里处理成功/异常 |

项目里 `KafkaTemplate.send` 一般是异步语义，适合「通知型」上下架。

### 关键参数（记住权衡）

**acks（消息确认）**

| 值 | 含义 | 速度 | 丢消息风险 |
| --- | --- | --- | --- |
| `0` | 发出去就当成功，不等服务器 | 最快 | 最高 |
| `1`（默认） | Leader 写入成功即可 | 中等 | 中等 |
| `all` | 参与同步的副本都收到才成功 | 最慢 | 最低 |

**retries**  
遇到临时性错误可以重试几次；重试间隔默认大约 100ms 量级。课里 demo 常配成 `5` 或 `10`。

**压缩**（可选）  
`snappy` / `lz4` / `gzip`：省网络和磁盘，多耗一点 CPU。带宽紧或消息大时有用。

一句话：要稳就倾向 `acks=all` + 合理 `retries`；要极限吞吐再往 `acks=0/1` 靠，并接受风险。

## 7）消费者详解：组、顺序、读到哪了

### 消费者组再强调一遍

- 组内多个消费者：共同消费一个 Topic，**分区**分给不同成员（并行）  
- 全员一个组 ≈ 队列模型  
- 每人不同组 ≈ 发布订阅模型  

### 消息顺序

Kafka **只保证单个分区内有序**，不保证跨分区全局有序。

若业务必须严格全局顺序 → Topic 只能一个分区（简单但吞吐差）。  
常见折中：同一用户/同一订单用同一 key，落到同一分区，保证「这条业务线」有序。

### 偏移量 offset：看到第几条了

消费者不靠「回执给队列删消息」，而是记录自己读到的 **offset**。  
崩溃或组员变化触发**再均衡**后，从提交过的 offset 继续。

提交时机不对会有两类坑：

| 情况 | 结果 |
| --- | --- |
| 处理完了但还没提交就挂了 | 再均衡后可能 **重复消费** |
| 还没处理完就提交了又挂了 | 再均衡后可能 **丢消息** |

提交方式：

- **自动提交**：`enable.auto.commit=true`，隔一段时间自动提交 poll 到的最大 offset，省事但对齐业务难  
- **手动提交**：`enable.auto.commit=false`，业务处理成功后再同步/异步提交，更可控  

「再均衡」= 消费者加减人时重新分配分区，这段时间最容易撞上重复或丢失，所以生产常关自动提交、处理完再手动提交。
