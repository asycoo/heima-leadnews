# 平台管理 · 需求 + 实战代码实现讲解

把《平台管理-需求说明》和 `day08-day09实战代码-不要发给学生` 对上后，核心结论是：

> **平台管理前端是一套壳，后端并不全写在 admin 服务里**；`admin-gateway` 按路径把请求拆到 `admin / wemedia / user` 三个微服务。

---

## 1. 整体架构（怎么串起来）

```text
浏览器
  ↓  :8803
Nginx
  ├─ /                 → admin-web 静态页
  └─ /service_6001/**  → 去掉前缀后转发到 admin-gateway
                           ↓
                     JWT 校验（登录放行）
                           ↓ 按路径路由（配置在 Nacos）
        ┌──────────────────┼──────────────────┐
        ↓                  ↓                  ↓
  leadnews-admin     leadnews-wemedia    leadnews-user
  /login/in          频道/敏感词/文章审核   用户实名认证审核
```

### 需求模块 ↔ 接口 ↔ 服务

| 需求模块 | 接口前缀 | 实际落点服务 |
|---|---|---|
| 登录 | `/login/in` | `heima-leadnews-admin` |
| 频道管理 | `/api/v1/channel/**` | `heima-leadnews-wemedia` |
| 敏感词 | `/api/v1/sensitive/**` | `heima-leadnews-wemedia` |
| 用户认证审核 | `/api/v1/auth/**` | `heima-leadnews-user` |
| 文章人工审核 | `/api/v1/news/**` | `heima-leadnews-wemedia` |

`admin` 模块本身几乎只做登录；业务数据大多在自媒体库、用户库里，所以审核/频道都复用已有服务，而不是再造一套。

## 2. 前端与 Nginx

需求里给了 Nginx 配置：

- `listen 8803`：打开管理后台页面
- `/service_6001/(.*)`：前端接口统一带此前缀，Nginx 剥掉前缀后打到网关

### 请求转发示例

| 浏览器请求 | 实际转发到网关 |
|---|---|
| `http://localhost:8803/service_6001/login/in` | `http://网关/login/in` |
| `http://localhost:8803/service_6001/api/v1/channel/list` | `http://网关/api/v1/channel/list` |

> 注意：参考代码里 `admin-gateway` 本地端口是 **51603**（需求示例写的 6001 是示意）。联调时 Nginx `proxy_pass` 要对准实际网关端口。

### Nginx 配置（需求原文）

```nginx
upstream  heima-admin-gateway{
    server localhost:6001;
}

server {
	listen 8803;
	location / {
		root D:/workspace/admin-web/;
		index index.html;
	}
	
	location ~/service_6001/(.*) {
		proxy_pass http://heima-admin-gateway/$1;
		proxy_set_header HOST $host;
		proxy_pass_request_body on;
		proxy_pass_request_headers on;
		proxy_set_header X-Real-IP $remote_addr;
		proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
	}
}
```

## 3. 网关：JWT + 路由

**需求**：平台端请求都走网关，校验 JWT，并路由到各微服务。

### 已补全内容

`heima-leadnews-admin-gateway`（端口 `51603`）现已具备：

| 文件 | 作用 |
|---|---|
| `AdminGatewayApplication.java` | 启动 + 注册 Nacos |
| `filter/AuthorizeFilter.java` | 全局 JWT 校验 |
| `util/AppJwtUtil.java` | token 解析/校验 |
| `resources/nacos/leadnews-admin-gateway.yml` | Nacos 路由示例（需手动贴到 Nacos） |

### 过滤器逻辑

```text
1. 取 request / response
2. 路径包含 /login → 直接放行
3. 取 header 中的 token
4. token 为空 → 401
5. 解析 JWT，校验是否过期 → 无效则 401
6. 从 claims 取 id，写入下游 header: userId
7. 放行
```

### Nacos 配置步骤

1. 打开 Nacos 控制台 → 配置管理 → 新建配置
2. Data ID：`leadnews-admin-gateway.yml`
3. Group：`DEFAULT_GROUP`
4. 格式：YAML
5. 内容直接复制：`admin-gateway/src/main/resources/nacos/leadnews-admin-gateway.yml`

路由摘要：

- `/login/**` → `lb://leadnews-admin`
- `/api/v1/channel/**`、`/api/v1/sensitive/**`、`/api/v1/news/**` → `lb://leadnews-wemedia`
- `/api/v1/auth/**` → `lb://leadnews-user`

## 4. 登录（需求 1.1）

**库表**：导入 `资料/leadnews_admin.sql`，使用 `ad_user`。

**实现位置**：`heima-leadnews-admin`

- Controller：`LoginController` → `POST /login/in`
- Service：`AdUserServiceImpl#login`

### 流程

1. 入参校验：`name`、`password` 不能为空
2. 按用户名查 `AdUser`
3. 密码校验：`md5(明文密码 + salt)` 与库中 password 比对
4. 成功：`AppJwtUtil.getToken(userId)` + 用户信息（清空 salt/password）一起返回

对应需求：**密码加盐验证，返回 token 和用户信息**。

## 5. 频道管理（需求 2）→ wemedia

**实现位置**：`WmchannelController` → `/api/v1/channel`

| 需求 | 接口 | 关键逻辑 |
|---|---|---|
| 新增 | `POST /save` | 同名校验，设 `createdTime` 后保存 |
| 列表 | `POST /list` | 名称模糊 + 状态精确 + 创建时间倒序 + 分页 |
| 修改 | `POST /update` | 若已有**已发布**文章引用该频道 → 禁止改/禁 |
| 删除 | `GET /del/{id}` | 仅禁用状态可删；仍被引用则不能删 |

`ChannelDto` 已补充 `status` 字段；`WmChannelServiceImpl#findByNameAndPage` 已补状态筛选与倒序。

## 6. 敏感词管理（需求 3）→ wemedia

**实现位置**：`WmSensitiveController` → `/api/v1/sensitive`

| 需求 | 接口 | 逻辑 |
|---|---|---|
| 新增 | `POST /save` | 词已存在则拒绝 |
| 列表 | `POST /list` | 名称模糊 + 创建时间倒序 + 分页 |
| 修改 | `POST /update` | `updateById` |
| 删除 | `DELETE /del/{id}` | 直接删 |

对 `wm_sensitive` 的 CRUD，和需求基本一致；列表已补 `orderByDesc(createdTime)`。

## 7. 用户认证审核（需求 4）→ user

**实现位置**：`ApUserRealnameController` → `/api/v1/auth`

| 需求 | 接口 | 逻辑 |
|---|---|---|
| 分页列表 | `POST /list` | 按 `status` 精确查 + 分页 |
| 审核通过 | `POST /authPass` | 状态改为 `9`（`UserConstants.PASS_AUTH`） |
| 审核拒绝 | `POST /authFail` | 状态改为 `2`（`UserConstants.FAIL_AUTH`），可写原因 |

### 通过后的关键动作（开通自媒体账号）

1. 查实名记录 → 查 App 用户
2. Feign 调 wemedia：`findWmUserByName`
3. 若没有则新建 `WmUser`（用户名/密码/盐与 App 一致）
4. App 用户 `flag` 置为 `1`（标识已是自媒体）

> 需求里「对接公安校验身份证」在参考代码里基本没落地，实战通常可简化/模拟。

## 8. 文章人工审核（需求 5）→ wemedia

自媒体自动审核未过时，文章状态会到人工审核（常见为 `3`）。Admin 端再审。

**实现位置**：`WmNewsController` → `/api/v1/news`

| 需求 | 接口 | 逻辑 |
|---|---|---|
| 列表 | `POST /list_vo` | 标题模糊、状态精确、分页；SQL 联表 `wm_user` 带出 `authorName` |
| 详情 | `GET /one_vo/{id}` | 查文章 + 作者名封装 `WmNewsVo` |
| 拒绝 | `POST /auth_fail` | 状态改为 `2`，写 `reason` |
| 通过 | `POST /auth_pass` | 先改 `4`，再调 `saveAppArticle` 创建 App 文章；成功后改为已发布，并回填 `articleId` |

### 审核状态常量

```text
WM_NEWS_AUTH_FAIL = 2   // 审核失败
WM_NEWS_AUTH_PASS = 4   // 人工审核通过（随后可变为已发布）
```

这和需求「驳回改 2 / 通过则创建 app 文章并更新自媒体状态」完全对齐。

---

## 9. 推荐落地顺序

1. 导 `leadnews_admin.sql`，加 `AdUser` 实体/Mapper（资料里已有类）
2. 建 `leadnews-admin`：只做登录
3. 建 `leadnews-admin-gateway`：JWT 过滤器 + Nacos 路由到 admin/wemedia/user
4. Nginx 部署 `admin-web`，代理 `/service_6001/` 到网关
5. 在 **wemedia** 补频道/敏感词/文章审核接口（很多已有）
6. 在 **user** 补实名列表与审核（开通自媒体用 Feign）

---

## 10. 一句话总结

平台管理不是「新建一个大而全的 admin 业务库」，而是：

> **admin 负责登录鉴权入口，gateway 统一鉴权转发，频道/敏感词/文章审核复用 wemedia，实名审核复用 user，前端经 Nginx 前缀代理访问网关。**
