# 用户行为 · 需求 + 实战代码实现讲解

对照《用户行为-需求》与 `day08-day09实战代码` 中的实现，核心结论是：

> **行为数据全部落 Redis，不写业务库**；按业务归属拆到三个服务：`behavior`（点赞/阅读/不喜欢）、`user`（关注）、`article`（收藏 + 详情行为回显）。

---

## 1. 整体架构

```text
App 前端（需登录）
        ↓
app-gateway（JWT 校验，把 userId 写入 header）
        ↓ 按路径路由
┌───────────────────┬────────────────────┬────────────────────┐
↓                   ↓                    ↓
leadnews-behavior   leadnews-user        leadnews-article
点赞 / 阅读 / 不喜欢   关注 / 取消关注       收藏 / 行为回显
        ↓                   ↓                    ↓
                     Redis（统一行为存储）
```

### 需求模块 ↔ 接口 ↔ 服务

| 需求 | 接口 | 落点服务 |
|---|---|---|
| 点赞 / 取消点赞 | `POST /api/v1/likes_behavior` | `leadnews-behavior` |
| 阅读 | `POST /api/v1/read_behavior` | `leadnews-behavior` |
| 不喜欢 / 取消 | `POST /api/v1/un_likes_behavior` | `leadnews-behavior` |
| 关注 / 取消关注 | `POST /api/v1/user/user_follow` | `leadnews-user` |
| 收藏 / 取消收藏 | `POST /api/v1/collection_behavior` | `leadnews-article` |
| 文章详情行为回显 | `POST /api/v1/article/load_article_behavior` | `leadnews-article` |

这与需求第 8 点完全一致：

- 行为数据存 Redis
- 点赞、阅读、不喜欢 → 新建 `heima-leadnews-behavior`
- 关注 → `heima-leadnews-user`
- 收藏与详情回显 → `heima-leadnews-article`

---

## 2. 为什么这样拆服务

| 服务 | 原因 |
|---|---|
| `behavior` | 纯埋点/行为采集，和用户账号、文章内容解耦，便于后续做推荐分析 |
| `user` | 关注关系本质是「用户 ↔ 用户」，归属用户域（我的关注 / 我的粉丝） |
| `article` | 收藏挂在文章上；详情页回显也是文章详情流程的一部分 |

共同点：登录用户从网关 header `userId` 取出，经拦截器放入 `AppThreadLocalUtil`。

---

## 3. Redis Key 设计

常量类：`BehaviorConstants`

| 行为 | Key 前缀 | 结构 | field / member |
|---|---|---|---|
| 点赞 | `LIKE-BEHAVIOR-{articleId}` | Hash | field=`userId`，value=DTO JSON |
| 不喜欢 | `UNLIKE-BEHAVIOR-{articleId}` | Hash | field=`userId` |
| 阅读 | `READ-BEHAVIOR-{articleId}` | Hash | field=`userId`，可累加 count |
| 收藏 | `COLLECTION-BEHAVIOR-{userId}` | Hash | field=`articleId`（entryId） |
| 我的关注 | `APUSER-FOLLOW-{userId}` | ZSet | member=`authorId`，score=时间戳 |
| 我的粉丝 | `APUSER-FANS-{authorId}` | ZSet | member=`userId`，score=时间戳 |

设计要点：

- 点赞/不喜欢/阅读：按**文章**建 Hash，方便看「这篇文章被谁操作过」
- 收藏：按**用户**建 Hash，方便看「我收藏了哪些文章」
- 关注双向 ZSet：同时维护「我的关注」和「对方粉丝」，方便两边列表查询

---

## 4. 登录与拦截器

`behavior` 模块示例：`AppTokenInterceptor`

1. 从请求头取 `userId`（网关 JWT 解析后写入）
2. 构造 `ApUser` 放进 `AppThreadLocalUtil`
3. 请求结束 `clear()`

各行为接口统一先判断：

```text
ApUser user = AppThreadLocalUtil.getUser();
if (user == null) → NEED_LOGIN
```

需求要求：行为相关操作、详情回显，App 端用户必须登录。

---

## 5. 点赞（需求 3）→ behavior

**实现**：`ApLikesBehaviorController` / `ApLikesBehaviorServiceImpl`

- 接口：`POST /api/v1/likes_behavior`
- 入参：`articleId`、`operation`（0 点赞 / 1 取消）、`type`（0 文章 / 1 动态 / 2 评论）

流程：

1. 校验参数与登录
2. `operation == 0`：若 Hash 中已有该用户 →「已点赞」；否则 `hPut`
3. `operation == 1`：`hDelete` 取消点赞

---

## 6. 阅读（需求 4）→ behavior

**实现**：`ApReadBehaviorController` / `ApReadBehaviorServiceImpl`

- 接口：`POST /api/v1/read_behavior`
- 入参：`articleId`、`count`（阅读次数；时长/比例等可放 DTO，非必要）

流程：

1. 校验参数与登录
2. 若该用户已有阅读记录 → 把旧 `count` 累加到本次
3. `hPut` 写回 Redis

对应需求：记录查看次数；阅读时长、比例、加载时长非必要。

---

## 7. 不喜欢（需求 5）→ behavior

**实现**：`ApUnlikesBehaviorController` / `ApUnlikesBehaviorServiceImpl`

- 接口：`POST /api/v1/un_likes_behavior`
- 入参：`articleId`、`type`（0 不喜欢 / 1 取消不喜欢）

流程：

- `type == 0` → `hPut`
- 否则 → `hDelete`

业务含义：标记后，后续推荐可过滤该类型/该文（本讲主要完成埋点写入；真正过滤在推荐链路使用这些 Redis 数据）。

---

## 8. 关注（需求 2）→ user

**实现**：`UserRelationController` / `ApUserRelationServiceImpl`

- 接口：`POST /api/v1/user/user_follow`
- 入参：`authorId`、`operation`（0 关注 / 1 取消），可带 `articleId`

流程：

```text
operation == 0（关注）
  ZADD APUSER-FOLLOW-{我}   authorId
  ZADD APUSER-FANS-{作者}   我的userId

operation == 1（取消）
  ZREM 两边对应 member
```

对应需求模型：

- 用户视角：一个用户可关注多个作者 → **我的关注**
- 作者视角：一个作者可有多个粉丝 → **我的粉丝**
- 作者来自实名认证开通自媒体后的 App 用户

---

## 9. 收藏（需求 6）→ article

**实现**：`ApCollectionController` / `ApCollectionServiceImpl`

- 接口：`POST /api/v1/collection_behavior`
- 入参：`entryId`（文章 id）、`operation`（0 收藏 / 1 取消）、`type`、`publishedTime`

流程：

1. 登录校验
2. 已收藏且再次收藏 →「已收藏」
3. `operation == 0` → `hPut(COLLECTION-BEHAVIOR-{userId}, entryId, dtoJson)`
4. 否则 → `hDelete`

---

## 10. 文章详情行为回显（需求 7）→ article

**实现**：`ArticleInfoController#loadArticleBehavior` / `ApArticleServiceImpl#loadArticleBehavior`

- 接口：`POST /api/v1/article/load_article_behavior`
- 入参：`articleId`、`authorId`

从 Redis 分别查询当前用户是否：

| 字段 | 判断方式 |
|---|---|
| `islike` | `LIKE-BEHAVIOR-{articleId}` 是否有该 userId |
| `isunlike` | `UNLIKE-BEHAVIOR-{articleId}` 是否有该 userId |
| `iscollection` | `COLLECTION-BEHAVIOR-{userId}` 是否有该 articleId |
| `isfollow` | `APUSER-FOLLOW-{userId}` 的 ZSet 是否含 authorId（`zScore != null`） |

返回示例：

```json
{
  "isfollow": true,
  "islike": true,
  "isunlike": false,
  "iscollection": true
}
```

前端据此高亮：赞、不喜欢、收藏、关注按钮。

---

## 11. 推荐落地顺序

1. 新建 `heima-leadnews-behavior` 模块（注册 Nacos，端口参考 `51805`）
2. 配置拦截器：从 header 取 `userId` 放入 ThreadLocal
3. 实现点赞、阅读、不喜欢三个接口（Redis Hash）
4. 在 `user` 实现关注（双向 ZSet）
5. 在 `article` 实现收藏 + `load_article_behavior`
6. app-gateway 增加对 `leadnews-behavior` 的路由
7. 联调：登录后操作行为 → 再调回显接口看四个布尔值

---

## 12. 一句话总结

用户行为这章不是改文章表/用户表，而是：

> **用 Redis 做行为埋点存储**；`behavior` 收点赞阅读不喜欢，`user` 管关注粉丝关系，`article` 管收藏并在详情页一次性回显四种关系状态，为后续热点分析与个性化推荐做数据准备。
